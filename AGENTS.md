# AGENTS.md

Guidance for AI coding agents working in this repository.

## Project Overview

PokemonRNGGuides is the pokemonrng.com site: MDX guides for Pokemon RNG manipulation plus interactive RNG tools. The UI is React + TypeScript (Vite, Ant Design, Emotion, Jotai). RNG logic is written in Rust under `rng_tools` and compiled to WASM.

All code must follow [CODE_STYLE.md](./CODE_STYLE.md). Read it before writing code, and run its self-review checklist before finishing.

## Commands

Bun is the package manager. Use `bun run <script>`, never npm/pnpm/yarn. Run the smallest command that validates the change. Always format `.rs`, `.ts`, and `.tsx` files after editing them, scoped to the touched files. Don't run other formatting or linting unless the task asks for it.

### Fast Feedback

- Type check: `bun run lint:ts:types`
- Format touched TS/TSX/MDX files: `bun prettier <file...> --write`
- Check formatting: `bun prettier <file...> --check`
- Rust tests: `bun run test:rust`
- Rust lint: `bun run lint:rust:code`
- Guides check: `bun run build:guides:check`

### Full Commands

These are slow or rebuild WASM. Ask before running them when a targeted check would do.

- Dev server, when Rust hasn't changed: `bun run scripts/dev-server`
- Rebuild Rust/WASM and start the dev server: `bun run dev`
- TypeScript lint suite: `bun run lint:ts`
- Full lint: `bun run lint`
- Full check: `bun run check`
- Production build: `bun run build`

## Project Structure

- `src/components/` - shared React UI components and form/table primitives.
- `src/rngToolsUi/` - tool-specific React screens and workflows.
- `src/rngTools/` - TypeScript-facing RNG domain helpers and generated bindings usage.
- `src/__generated__/` - generated by `scripts/build-guides.tsx`; do not edit.
- `guides/` - MDX guide content.
- `scripts/` - Bun scripts for builds, guides, and generated data.
- `rng_tools/` - Rust crate compiled to WASM.
- `dist/` - generated build output; do not edit.

## Working Rules

- Respect the existing working tree. Do not revert, overwrite, or clean up unrelated changes.
- Keep edits narrowly scoped to the task.
- Prefer existing components, utilities, and patterns over new abstractions.
- Use ASCII in new files unless the surrounding file already uses Unicode or the content clearly needs it.
- Never modify a file outside of the project.

## Frontend Guidelines

- Match the app's existing UI conventions and the components in `src/components`.
- Avoid layout churn and unrelated visual redesigns.
- Ensure labels, buttons, and dynamic text fit across expected viewport sizes.
- The project uses React Compiler. Don't add `React.useMemo`, `React.useCallback`, or `React.useEffect` unless the linter or a real side effect requires it.
- Use existing icons, Ant Design components, and local wrappers before adding UI dependencies.
- Put user-facing explanations in MDX guides or tooltips, not in tool source.

## TypeScript Guidelines

- Reuse domain types from existing modules such as `~/rngTools` and `~/types`.
- Use existing formatting helpers for user-visible numbers, methods, maps, and Pokemon-specific display text.
- Use structured helpers instead of ad hoc parsing.
- Keep imports aligned with existing path aliases and lint rules.

### Persisted State Migrations

- Any schema change for persisted atoms must include a migration path. Do not rely on persisted state merging with initial values.
- For newly added persisted fields, parse older data with `optional()` plus `default()`, or a small `transform()` that fills the current default.
- For larger shape changes, use a versioned `z.discriminatedUnion()` with a `version` tag and `transform()` older versions into the current shape.
- Follow the Gen 5 timer migration in `src/rngToolsUi/timer/gen5/standard.tsx`.

## Rust/WASM Guidelines

- Keep Rust changes localized under `rng_tools`.
- Run `bun run test:rust` after Rust logic changes.
- After changing exported Rust types or functions, rebuild WASM (`bun run build:rng_tools`) before type checking TypeScript.

## Guide Content

- After editing MDX frontmatter, ask the maintainer to run `bun run build:guides` to regenerate `src/__generated__`.
- Use `bun run build:guides:check` to validate guide changes.

## Boundaries

### Always

- Read files and list directories.
- Edit files in this repository for the requested task.
- Run targeted format, type-check, lint, build, or test commands.

### Ask First

- Installing or upgrading dependencies, or changing lockfiles.
- Git commits, pushes, branch changes, rebases, resets, or stashes.
- Deleting files or generated directories.
- Running full-suite checks when a targeted check would be enough.
- Commands that need network access or write outside the repository.

### Never

- Don't edit generated output (`dist/`, `src/__generated__/`, WASM build artifacts). Instead, edit its source and regenerate.
- Don't silence type errors with `as X`, `as unknown as X`, `any`, or `unwrap` on fallible results. Instead, fix the types with constraints the compiler checks. When a type-safe fix is impractical, explain why and let the maintainer decide.
- Don't restore code that history shows was removed on purpose. Instead, ask the maintainer why it was removed.

## Validation

- Before finishing, run the most relevant practical validation:
  - TS/React edits: `bun run lint:ts:types`, plus file-scoped Prettier checks.
  - Rust edits: `bun run test:rust`.
  - Guide edits: `bun run build:guides:check`.
- If a command can't run because of dependencies, sandboxing, generated artifacts, or time, say so.

## PR Expectations

- Keep diffs small and focused.
- Include or update tests when behavior changes or risk warrants it.
- Mention validation performed and any skipped checks in the final response.
